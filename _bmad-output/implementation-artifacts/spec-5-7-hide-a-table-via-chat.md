## Intent

**Problem:** An Admin can delete nothing structural safely today: a "delete the Jobs table" request lands as `out_of_scope` and gets a generic decline (Story 5.5 shipped only column-hide). The epic's safety promise (FR98) is that a table-delete request is satisfied non-destructively by a reversible HIDE — the table drops off the dashboard, all rows in `records` stay intact, and it is restorable. The persisted table-visibility mutator, its route, and the add-table Undo were explicitly deferred from Story 5.5 (`deferred-work.md`), and the app currently has no way to hide a whole table or restore a hidden one.

**Approach:** Teach the editor one new operation, `hide_table`, that the model returns for a delete/remove/hide request naming an exactly-identifiable table. Unlike `hide_field` (which applies immediately), a table hide is consequential, so the route does NOT mutate on `hide_table`: it resolves the target and returns an OFFER (`confirm` result) carrying the `tableKey`. The chat renders a reassuring offer with an inline "Hide the table" confirm button; clicking it calls a NEW direct, non-LLM `POST /api/schema/tables` (mirroring Story 5.6's `/api/schema/views`) which runs a new guarded `setTableVisibility(identity, tableKey, true)` mutator, then shows a confirmation and a "show again" Undo. A newly applied `add_table` chat result also gains an Undo that hides the just-added table via the same endpoint. Hidden tables are listed in a new Admin-only "Hidden tables" section in Settings, each with a Restore control that calls the same endpoint with `setTableVisibility(..., false)`. All copy is server/`ChatAssistant`/`SlugDashboard` i18n (en + fr), reassuring, no em-dash, and never exposes JSON/SQL/schema/stack.

## Boundaries & Constraints

(Epic-5 invariants in `epic-5-context.md` apply; below is specific to this story.)

**Always:**
- `hide_table` is added to `PERMITTED_OPERATIONS` so it passes the same Story 5.4 fence (`assertEditorOperationAllowed` = allowlist + raw-SQL discard) as the other ops. The model returns it for a delete/remove/hide request that resolves to EXACTLY ONE existing table (named, or the single current table); ambiguous/none → `needs_clarification`.
- The edit route's `hide_table` branch performs NO mutation. It validates `tableKey` is a non-empty string AND resolves it against the `tables` summary the model was shown (out-of-summary/hallucinated → reassuring `declined`), then returns `kind: "confirm"` carrying `tableKey` + `label`. If hiding would remove the LAST visible table (`!canHideTable`), it returns a reassuring `declined` instead of an offer (never an empty dashboard).
- The actual hide/restore runs ONLY through the new direct `POST /api/schema/tables`, Admin-gated server-side (`requireAdmin` + `membership.slug === slug` + `resolveWritableOrgIdentity`) exactly like `/api/schema/columns` and `/api/schema/views`; a Member gets 403 and the controls are not rendered for Members. Its body is a discriminated union on `action: "hide" | "restore"`, both carrying `{ slug, tableKey }`.
- `setTableVisibility(identity, tableKey, hidden)` mirrors `setFieldVisibility`: read the RLS-scoped schema, 400 (`AppError`) if `tableKey` is absent, and when hiding, 400 if `!canHideTable(schema)` (would empty the dashboard — re-checked here, not only at offer time); apply the pure `hideTable`/`showTable` transform; write the full definition back; return `{ tableKey, hidden }`.
- The confirm button, the add-table Undo, the chat show-again Undo, and the Settings Restore all go through `POST /api/schema/tables`. After any hide/restore, `router.refresh()` re-renders the dashboard/Settings from the server's `visibleTables`.
- A newly applied `add_table` result carries `undo: "hide-table"` + `tableKey` so the chat bubble offers an Undo that hides the just-added table (no offer step — an explicit Undo click is the confirmation).
- New copy lives only in `ChatAssistant` (en+fr) and `SlugDashboard` (en+fr), is reassuring and non-technical, contains no em-dash, and never mentions JSON, SQL, schemas, or errors.

**Never:**
- No destructive migration, DDL, SQL generation, table/row drop, or data mutation — setting the table-level `hidden` flag is the only state change; rows in `records` are always retained and true table deletion stays unsupported.
- No per-view-tab or per-table-tab "Hide table" overflow control in this story — table hide is reachable via chat (offer+confirm) and the add-table Undo; restore is the Settings surface. (The tab-menu hide control is out of scope.)
- The model never drives the mutation directly: `hide_table` only yields an offer; no immediate hide on the model path (contrast `hide_field`).
- Never change Story 5.4's verb/raw-SQL guards, the `add_field`/`hide_field`/`add_view`/`remove_view` branches, the `needs_clarification`/`out_of_scope` flows for other requests, the degraded LLM-failure path, or auth/role gating.
- Never expose a raw `tableKey`, JSON, SQL, schema object, or error stack in any user-facing message.

## Design Notes

A table hide is the mirror of `hide_field` (Story 5.5) at the table grain — same append-only `hidden` flag, same reuse of a guarded read-verify-write mutator — but with two deliberate differences. (1) It is gated by an explicit confirmation: hiding a whole table removes a dashboard tab, a bigger consequence than hiding one column, so the model's `hide_table` yields an OFFER (route returns `confirm`, no mutation) and a button click drives the actual write through the direct, non-LLM `POST /api/schema/tables` — a button carries no natural language and must not spend a Gemini call (the Story 5.6 button→direct-endpoint precedent). (2) It enforces `canHideTable` both at offer time (for a good message) and in the mutator (the real guard), so an Admin can never empty their own dashboard. Restore is a plain `setTableVisibility(..., false)` reachable from Settings and from the chat show-again Undo; the add-table Undo is the same `hide` action with no offer (an explicit Undo click is itself the confirmation). `hide_table` joins `PERMITTED_OPERATIONS` (rather than being exempted like the conversational kinds) to keep ONE uniform allowlist + raw-SQL fence over every model-driven operation, even though its route handler offers rather than applies.
