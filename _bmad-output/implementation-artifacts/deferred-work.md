- source_spec: `_bmad-output/implementation-artifacts/spec-2-1-claim-app-via-magic-link.md`

- source_spec: `_bmad-output/implementation-artifacts/spec-2-1-claim-app-via-magic-link.md`
  summary: `finalizeClaim` promotes the session org across four non-transactional writes (membership → slug → clear records → consume token) with no rollback.
  evidence: A mid-sequence failure (e.g. the `records` clear throws after membership + slug are set) leaves a half-promoted org; the callback redirects to `?claim=error` with the token unconsumed. Harm is low — the steps are individually idempotent and a retry of the same (unconsumed) token self-heals, and only the user's own synthetic rows are affected (no data leak). A correct fix wraps the promotion in a single Postgres function/transaction (a new RPC), which is more surface than a patch. Settling it needs that transactional RPC plus a mid-sequence-failure test.
