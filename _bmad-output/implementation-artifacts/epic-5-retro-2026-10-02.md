### Aggregate views

- **[A1] Route-auth/identity scaffolding is re-inlined across all five schema routes — Med, fix-now (5th recurrence).** `edit/route.ts:164-194`, `views/route.ts:57-89`, `tables/route.ts:59-91`, `fields/route.ts:53-83`, and `columns/route.ts:51-86` each hand-roll the identical 4-step chain — `getCurrentUser()` → `requireAdmin(user, createAdminClient())` → `membership.slug !== slug` cross-org check → `resolveWritableOrgIdentity(slug, user.id)` — including byte-identical guard comments. The helper that collapses exactly this, `resolveWritableAdminIdentity(slug, user)` (`route-helpers.ts:154-164` = `resolveAdminIdentity` admin+slug gate + `assertWritable`), already shipped in Epic 12 and is used by `business-profile/route.ts:112`. This is the **same recurring route-auth-duplication pattern flagged in the epic-3 [A2], epic-4 [A1], epic-7 [A1/A2], and epic-12 [A2] retros** — now its 5th consecutive recurrence, in a fresh subsystem, with the fix already available. *Remedy:* replace steps in all five routes with `const user = await requireUser(); const identity = await resolveWritableAdminIdentity(slug, user);` (keep GET siblings on the read resolver). Auth is correct everywhere today — this is maintainability, not a security hole.
- **[A2] `schema-mutate.ts` is missing `import "server-only"` — Med, fix-now.** `src/lib/data/schema-mutate.ts:1` starts with `import type { SupabaseClient }` and carries **no** `server-only` guard, while the sibling data/guard modules do: `records.ts:1`, `validator.ts:1`, `route-helpers.ts:1`, `prompts.ts:1`, all five schema `route.ts:1`. It performs RLS-scoped `org_schemas` writes — exactly the class `route-helpers.ts:22-25` documents as "must never enter a client bundle." No leak occurs today (only server routes import it, confirmed by the architecture-delta check), but it diverges from the established convention. *Remedy:* add `import "server-only";` as line 1. (Recurrence of epic-3 item 16 / epic-12 item 35, which added `server-only` to data modules for the same reason.)
- **[A3] `edit/route.ts` POST is an ~590-line, 8-branch dispatcher — Med, defer (cleanup).** The single `POST` handler (`route.ts:159-748`, file is 773 lines) fans out to eight `output.kind` branches (`add_field` :283, `add_table` :344, `add_view` :409, `hide_field` :501, `remove_view` :594, `hide_table` :672, plus clarify/out_of_scope), each repeating shape-guard → `try { mutator } catch { handleMutateError }` → build result. Cohesive (one endpoint) but past comfortable size. *Remedy:* extract a per-kind handler map.
- **[A4] Six mutators in `schema-mutate.ts` share a copy-pasted read-validate-write + catch skeleton — Med, defer.** `setFieldVisibility` :67, `addRelationField` :134, `addField` :206, `addTable` :281, `addView` :349, `removeView` :418, `setTableVisibility` :485 each repeat verbatim the `getSchema` + `if (current.error||!current.data) throw AppError(500,"writeFailed")` read, the identical `.from("org_schemas").update({definition, updated_at}).eq("organization_id", orgId)` write, and the identical trailing AppError catch. *Remedy:* a `withSchemaWrite(identity, schema => next)` higher-order helper; each mutator supplies only the pure transform. **Note:** this per-write `getSchema` round-trip is exactly what the still-open **epic-3 item 21** ([A5]) asked to eliminate — the new mutators expanded the pattern rather than addressing it.
- **[A5] `schema-chat-client.ts` repeats the fetch→json→error-check boilerplate 5× — Low/Med, defer.** `postSetColumnVisibility` :82, `postHideTable` :120, `postRestoreTable` :156, `postRemoveView` :192, `postRestoreView` :231 each repeat the same fetch/try-catch/json/`if(!res.ok||body?.error) throw` block (compare :88-108 ≡ :126-144 ≡ :162-180). *Remedy:* a single `postSchemaAction<T>(url, body)` wrapper.
- **[A6] `ChatPanel` message state is an informal boolean state machine — Med, defer.** The assistant `ChatMessage` variant carries 8 optional discriminator fields (`applied`, `appliedView`, `offerTable`, `appliedTableUndo`, `hiddenTable`, `isHide`, `isView`, `isViewRemoved`, `ChatPanel.tsx:70-124`) and the rendered variant is computed by a deeply nested ternary (`:457-486`). Cohesive to one panel but fragile as the op set grew across stories. *Remedy:* replace the boolean soup with a single `kind` discriminant on the message object.
- **`validator.ts` (1172 lines) is large but cohesive — accept (not a finding).** Every export is one pre-persist validation gate sharing the same primitives (`keyIsBlockedVerb` :172, `RAW_SQL_VERB_RE` :195, `normalizeTableName`); the generation/editor validators are deliberately separate (documented at `validator.ts:544-548`). Single responsibility intact. Recorded so it is not mistaken for a god-class later.
- **Architecture delta — clean.** No `"use client"` component imports a server data module at runtime (ChatPanel reaches the server strictly through `fetch` in `schema-chat-client.ts`; the only cross-boundary imports are compile-erased `import type`, an established codebase convention). The edit route never reaches around the guarded mutate layer — every write goes through `schema-mutate` (`route.ts:298/366/454/541/625`); its one direct `getSchema` is read-only. No import cycle (`schema-mutate → overrides/validator` and `edit/route → prompts/validator` are DAGs). The one new cross-route edge — hide_table returns a `confirm` offer whose write crosses to `POST /api/schema/tables` — is deliberate and guarded (the mutator re-checks `canHideTable`, `schema-mutate.ts:510`).
