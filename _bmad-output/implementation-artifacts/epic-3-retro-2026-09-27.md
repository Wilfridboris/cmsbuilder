The JSX sub-components below the function are cleanly delegated; the risk is the concentration of hook/state logic in one function. Extract `useFilterSortState`, `useAddDraft`, `useRecordActions`.
- **[A2] Six duplication clusters — Med/Low, defer (cleanup).**
  - `resolveIdentity` + `json` + `handleError` helpers copy-pasted across all records/schema route files (`records/search/route.ts:33-58`, `schema/fields/route.ts:46-71`, and siblings), and `[id]/route.ts` inlines `resolveIdentity` twice (DELETE `:70-86`, PATCH `:137-151`) instead of extracting. Verified directly. Extract into `src/app/api/records/_lib.ts`.
  - `resolveRelationLabel` adapter byte-identical in `RecordsView.tsx:266-272` and `RelatedRecordsList.tsx:144-151`.
  - Filter/sort state handlers duplicated between `RecordsView.tsx` and `RelatedRecordsList.tsx` (with a `cycleSort` signature divergence — see A2b).
  - `RelationFilter` type declared twice (`records.ts:23`, `records-client.ts:40`).
  - `crypto.randomUUID` fallback idiom in `RecordsView.tsx:352-355` and `useRecordMutations.ts:86-88`.
- **[A2b] `cycleSort` behavioral divergence — Low, note.** `RecordsView.tsx:298` takes a `field` arg (header-click cycles any field); `RelatedRecordsList.tsx:172` takes none (no-op when no sort is active). Same `RecordsToolbar` `onSortToggle` prop, subtly different behavior at the reverse-list boundary.
- **[A3] Concurrency conflict detected by matching an English sentence — Med, fix now.** `mutate.ts` (concurrency path) throws `AppError(409, "This record changed since you loaded it…")` — a full sentence — which `[id]/route.ts:36,96,158` re-detects via a `CONCURRENCY_MESSAGE === result.error` string compare. Every other error uses a code sentinel (`"invalidReference"`, `"writeFailed"`). If the sentence is ever reworded, conflict detection silently degrades to generic `writeFailed`. Throw a stable code (`"versionConflict"`) instead.
- **[A4] Client component imports server-layer file; `records.ts` has no `server-only` guard — Low, defer.** `DeleteConfirmDialog.tsx:16` (a `"use client"` file) imports `REFERENCE_COUNT_CAP` from `src/lib/data/records.ts`, which is otherwise server-only but lacks the `import "server-only"` guard. Type-only resolution keeps it harmless today; add the guard and move the constant to `records-client.ts`.
- **[A5] `mutate.ts` re-reads the schema on every write — Low, defer (perf).** `mutate.ts:7,254` calls `getSchema` per insert/update for referential-integrity checks — a redundant round-trip when the route already has the schema. Pass the schema into `assertRelationReferencesExist`.

### Spec-to-implementation reconciliation

10 of 11 mandatory technical decisions **confirmed** in code: guarded writes (no service-role, no cookie reads in the data layer), optimistic concurrency via `version`, soft-delete via `deleted_at`, mandatory optimistic-UI sequence, real-time `invalidateQueries`-not-`setQueryData` handler (`realtime.ts:38,46-52`; `useRealtimeRecords.ts:62-71`), app-layer referential integrity (`mutate.ts:247-319`), translated non-error empty states, i18n (no hardcoded user-facing strings), metadata-only Admin column-hide, and CRUD independent of the LLM.

- **[S1] Typeahead uses `->>` text extraction — accepted deviation, reconcile spec.** `records.ts:162,168` — `searchRelationRecords` uses `data->>${displayFieldKey}` for the ILIKE substring match and ORDER BY. This is the one relation-read that containment (`@>`) cannot serve (substring search). The code comment (`records.ts:139-141`) already acknowledges a `pg_trgm` index as a deferred scale follow-up. The epic-context rule "reference reads use containment, never text extraction" is too absolute; reconcile it to carve out the typeahead display-field path. **Residual risk:** the `data->>x ILIKE '%…%'` scan is un-indexed and will not meet the declared ~500ms p95 over 50k rows without the deferred `pg_trgm` index — track in deferred-work.

### Diff-scope review (adversarial / edge-case / verification-gap)

- **[D1] Relation display-field key interpolated into PostgREST column expression — checked, NOT exploitable.** Raised as HIGH injection (`records.ts:162,168`, `data->>${displayFieldKey}` and `.order(...)`). Re-verified: `displayFieldKey` comes from `resolvedDisplayFieldKey(targetTable)` reading the stored schema, and every stored field key passes through `normalizeTableName`, which constrains keys to `[a-z0-9_]` (`validator.ts:68,241,445`; `utils.ts:50-`). No hostile character can reach the interpolation. Recorded as clean; a defense-in-depth key-allowlist at the query site is optional, not required.
- **[D2] Admin RBAC resolves the most-recent org only — accepted MVP constraint (dup of epic-2 F10).** `requireAdmin` → `resolveUserOrgMembership` orders `org_members` by `created_at desc limit 1` (`org.ts:93-99`). **Resolved:** multi-org membership is deliberately unreachable in the MVP — the invite flow returns `409 accountExists` for an existing account not already in this org (`invite.ts:119-125`), and claim creates the sole org, so every user has exactly one membership and the most-recent choice is always correct. The data model is built for eventual multi-org (`auth_org_ids()` returns a set; RLS is `organization_id IN (...)`), so this becomes a real bug only once cross-org membership lands. This is the **same finding the epic-2 retro logged as F10 (LOW)** and deferred to bundle with F4 (consolidate the resolvers) — not a new epic-3 defect. Disposition: accept as MVP constraint; keep bundled with epic-2 F4/F10. **Recommended cheap hardening:** make `resolveUserOrgMembership` assert ≤1 membership (fail loud) instead of silently `LIMIT 1`, so if multi-org ever becomes reachable a wrong-org authz decision surfaces as an error rather than a silent bug.
- **[D5] `"on"` date filter uses exact epoch-ms equality — Med, fix now.** `filter-sort.ts:197-198` — `case "on": return cell === a`. Verified. For `datetime` fields this is effectively always false (a timestamp never equals a date-string's midnight-UTC ms); for `date` fields it works only when both parse to the identical millisecond. Compare calendar date-parts (or ISO date prefixes) instead.
- **[D4] Soft-delete leaves dangling relation ids with no repair path — Low/Med, defer (data hygiene).** `mutate.ts:201-231` — deleting a referenced record soft-deletes it; referencing rows keep the dead id and render as "archived" (this part is per spec). But a later PATCH that omits the relation field never re-validates it, so the dangling id persists indefinitely; no path in this epic repairs it. Acceptable for MVP (matches the archived-target spec), but track a cleanup/repair follow-up.
- **[D10] No size/field-count cap on `data` payload — Low, defer.** `records/schemas.ts` create/update use `z.record(z.string(), z.unknown())` — an authenticated member can store arbitrarily large JSONB, bounded only by infra limits. Add an application-level cap.
- **[D8] `countReferencingRecords` is sequential with no timeout — Low, defer (perf).** `records.ts:263-283` awaits one round-trip per (table, field) pair; on a large schema this slows the delete dialog's open. Parallelize with `Promise.all` and add a timeout.
- **[D6] No `CHANNEL_ERROR`/`TIMED_OUT` handling in realtime — Low, defer.** `useRealtimeRecords.ts:62-71` invalidates on `postgres_changes` and re-invalidates on `SUBSCRIBED` (reconnect), but a permanent socket failure surfaces no error and has no fallback poll — dashboard silently goes stale.
- **[D11] `[id]` path param not validated as UUID — Low, defer.** `[id]/route.ts:56-58` checks truthiness only; a non-UUID yields a Postgres `22P02` → generic 500 instead of a clean 400. Safe (parameterized), just a wrong status code.
- **[D3] Version incremented application-side — Low, note.** `mutate.ts` sets `version: expectedVersion + 1` in the UPDATE payload. The `.eq("version", expectedVersion)` guard makes concurrent writes safe; the only risk is divergence if another writer bypasses `mutate.ts` or a DB trigger also increments. No such trigger was found.
- **[D7] Optimistic update keyed to the relation-filter query key — Low, accept.** `useRecordMutations.ts:137` — the same record shown under two different relation-filter keys updates only the matching key; the other view self-corrects on the next invalidate. Cosmetic.
- **[D9] Relation search fetches not aborted on popover close — Low, accept.** `RelationPicker.tsx` — TanStack key isolation prevents stale overwrite (the agent's initial "stale response" concern self-corrected); orphaned in-flight fetches are harmless.
- **[D12] Delete confirm active while reference count loads — Low, accept.** `DeleteConfirmDialog.tsx` — by design ("a count failure never blocks the delete"), but a fast click can confirm before the advisory count renders.

### User-raised: the empty-cell placeholder dash

`Generate.cellEmpty` was an **em-dash `—`** (`en.json:48`, `fr.json:48`), rendered by `formatCell` for every null/blank/empty value across the authenticated dashboard (`[slug]/page.tsx`), demo dashboard, and record detail. Besides reading oddly, an em-dash violates the project's own no-em-dash-in-user-facing-copy rule.

**Fixed (implemented + verified this session, via `/web-uiux-architect`).** Chosen alternative: a visually **blank cell + screen-reader-only "Empty"/"Vide"** label (Airtable/Notion/Linear pattern). Changes: `formatCell` now returns `""` for blank values (display decoupled from the accessible label); `CellStrings.empty` is repurposed as the sr-only label (`cellEmpty` → "Empty"/"Vide"); a new shared `src/components/dashboard/CellText.tsx` renders `<span className="sr-only">{label}</span>` for blanks and the formatted value otherwise; all render sites migrated (`InlineEditCell`, `RecordDetail`, `RecordReverseListDialog`, `DemoDashboard.renderCell`). 48px touch targets and edit affordances preserved. Verified: `tsc --noEmit` clean, `eslint` clean, `vitest` 480/480 green (`format.test.ts` blank assertions updated `"—"` → `""`). Changes are in the working tree, pending commit.
