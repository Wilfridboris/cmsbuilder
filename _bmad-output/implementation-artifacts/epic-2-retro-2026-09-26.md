## Findings

Each finding carries a source and two dispositions (this-instance / upstream-lesson). Findings on `generate/route.ts` concern **epic-1 code not touched by this epic**; they surface here as cross-cutting debt and are attributed as such, not counted against epic 2.

### Security / RBAC (the trust foundation)

The RBAC spine is genuinely server-enforced from the database, not the UI and not the JWT. The highest-risk classes were checked and are **clean** (see Checked-clean). Two findings, which together form one trap:

**F1 (MED) — Claim finalize unconditionally rewrites the caller's global `user_metadata.role` to `admin`.**
`src/app/auth/callback/route.ts:123-131` runs `supabase.auth.updateUser({ data: { role: "admin", ... } })` on every claim finalize. Any authenticated user — including an invited Member — can visit `/generate` (mints a fresh anonymous `sb_gen_session` demo org), then POST `/api/claim` with their own email and finalize, which (a) creates a *new* org where they are legitimately Admin and (b) blindly stamps `role: "admin"` onto their existing account's metadata. Corroborated first-hand: `callback/route.ts:120-131` + `claim.ts` finalize. Impact is **bounded today** — the claim is keyed to the session-cookie org (not the org they were invited to, so it is not a takeover), and no enforcement path reads `user_metadata.role` (authz reads `org_members`, see Checked-clean). It becomes a live privilege escalation the moment any future code trusts the metadata role. Disposition: **fix now** (do not unconditionally assert `admin` on an account that may be a Member elsewhere; write the role tied to the org actually bootstrapped, or drop the metadata role write entirely since it is unused for authz). Upstream lesson: see F2.

**F2 (LOW, but pairs with F1) — Comments claim the JWT metadata role is "what 2.4 enforcement reads." It is not.**
`src/lib/invite/invite.ts:31-34` and `src/lib/auth/rbac.ts:14-17` describe `user_metadata.role` as "the JWT convenience 2.4 enforcement reads," but `requireAdmin` (`rbac.ts:43-44`) and the layout/nav read role authoritatively from `org_members` (DB) via `resolveUserOrgMembership` (`org.ts:89-111`); grep confirms no `user_metadata.role`/`app_metadata.role` is read anywhere in `src` for authz. Not exploitable, but a dangerous latent trap: a dev trusting these comments could switch enforcement to the client-influenceable JWT copy — which F1 has already pre-loaded with `admin`. Disposition: **fix now** (cheap: correct the comments to state the DB-source design; removes the trap). Upstream lesson: when a later story overrides a technical decision, reconcile the sibling comments/spec in the same change.

**F6 (MED) — `claim.ts` (272 lines) bundles many concerns; `claim/route.ts` holds domain Zod schemas.**

### Hardening verification (2.5 / 2.6 — the carried F7/F8 fixes)

Both fixes **verified FIXED**, with strong bidirectional test coverage, and fully contained to their own files (`git show --stat`: 2.5 → `validator.ts` + test only; 2.6 → `utils.ts` + test only; no leakage into `route.ts`/`provision.ts`/`mutate.ts`/generation code).

- **2.5 (validator false-reject) — FIXED.** The label-side blocked-keyword check is entirely removed; the key-side check is now whole-word (`BLOCKED_KEYWORD_RE = /\b(DROP|GRANT|TRUNCATE|DELETE|EXEC)\b/i`, `validator.ts:90-97`) applied to the normalized key only, at both table (`:155`) and field (`:202`) sites. Because normalization maps separators to `_`, it rejects only a *bare* verb key (`drop`, `delete`, …) and accepts `dropoff`/`grants`/`drop_off_time`/`deleted`; labels are never checked. Real protections intact (reserved-key `:158,205`, type allowlist `:186-196`, empty `:152,199`, `reportRejection` `:114`). Tests pin "Grants"/"Drop-off time"/"Deleted?" accepted and bare-verb + reserved + relation + empty rejected (`schema-validator.test.ts:111-215`). Residual (LOW, by-design, spec-acknowledged): a multi-token key embedding a real verb (`drop_table`) passes — keys are inert JSONB strings, never SQL identifiers, so no injection outcome. Disposition: **accept-as-is**.
- **2.6 (non-ASCII key normalization) — FIXED.** NFD-decompose + combining-mark strip (`/[̀-ͯ]/g`) *before* the original lowercase/strip pipeline (`utils.ts:50-58`); deterministic FNV-1a `stableHash` fallback → `field_<hash>` for empty folds (`:15-24,60-67`). Verified: `numéro→numero`, `coût→cout`, distinct siblings do not collapse, ASCII output byte-identical (NFD is a no-op on ASCII; `normalize.test.ts:72-91` asserts equality vs the legacy pipeline — a genuine regression guard), and non-Latin (`顧客`/`العميل`/`Кириллица`/`日本語`) yields deterministic non-empty `[a-z0-9_]` keys. Residual (LOW, spec-acknowledged): accented/ASCII-twin fold collision (`région`+`region`) and 32-bit FNV collision both backstopped by the validator's duplicate-key check → same fallback outcome as before. Disposition: **accept-as-is**.

### Latent correctness seam (note, not yet a defect)

**F10 (LOW) — `requireAdmin` resolves the caller's "most-recent" membership only.**
`requireAdmin` → `resolveUserOrgMembership` orders by `created_at DESC LIMIT 1` (`org.ts:96-99`). Safe today because multi-org membership is unreachable (an existing account invited elsewhere gets `409 accountExists`, `invite.ts:125`), but once cross-org membership lands, an Admin-of-org-A who is a Member-of-org-B could resolve to the wrong org's role. Disposition: **defer** (revisit with the multi-org picker; bundle with F4).

### Checked-clean (verified, not findings)

- **Invite verifies the CALLER is an admin server-side** before any create/send (`invite.ts:110` `requireAdmin`, role from DB), with the route's null-session 401 as an independent backstop (`invite/route.ts:54-57`). A Member calling `POST /api/invite` directly is 403'd before any side effect.
- **Authz never reads a client-controllable role** — the authority is `org_members.role`; no `user_metadata.role`/`app_metadata.role` read for authz anywhere in `src`.
- **Invite is org-scoped (no IDOR)** — invitee membership inserted with the *inviter's* resolved `orgId` (`invite.ts:114,147-153`); an existing user in another org → 409, not a silent cross-org move.
- **Settings page** re-checks `getCurrentUser` + `requireAdmin` + bounces on `membership.slug !== slug` (`settings/page.tsx:37-60`); UI hiding (`DashboardNav.tsx:53`) is redundant, not the sole gate.
- **Identity uses `getUser()` (JWT-validated) not `getSession()`** (`session.ts:23`, `middleware.ts:69`); the pre-auth `sb_gen_session` cookie is HMAC-signed + `timingSafeEqual`-verified.
- **No open redirect** — all callback/confirm redirects build `new URL(serverPath, req.nextUrl.origin)`; no user-supplied `next`/`redirect` honored.
- **Service-role confined to bootstrap** — admin client used only for claim/invite membership provisioning + org/role reads; tenant `records` reads go through the RLS-scoped client (`[slug]/page.tsx:44`), writes through `mutate.ts`. No raw service-role tenant write.
- **Login never clobbers role** — `/api/login` sends no `data.role` (`login/route.ts:109-115`); `shouldCreateUser:false` + swallowed no-user outcome for anti-enumeration.
- **Claim finalize is idempotent** — token consumed via `consumed_at`, expiry enforced, membership insert idempotent on unique(org,user).
- **i18n: full EN/FR parity** — both `en.json`/`fr.json` 184 lines, identical key trees across the new `Claim`/`Login`/`Settings`/`DashboardNav`/`SlugDashboard` namespaces, every FR value real French, interpolation tokens matched; no hardcoded user-facing strings in any epic-2 UI/route file; ARIA/`role` notices translated.
