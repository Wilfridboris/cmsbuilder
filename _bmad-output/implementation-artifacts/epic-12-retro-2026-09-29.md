### Declared invariants I1–I8 — ALL HOLD (headline)

Two independent agents verified every binding invariant against the shipped code with source refs. This is the core acceptance evidence for a compliance-critical epic.

- **I1 Numbering — HOLDS.** Per-org counter row incremented atomically inside the issue transaction (`update ... set next_number = next_number + 1 ... returning next_number - 1`), never `max()+1` — `20260928120900_issue_invoice.sql:66-95`, `20260928122000_issue_credit_note.sql:66-96`. Disjoint invoice/credit-note counter tables (`20260928120800`, `20260928121800`). Zero-pad, no-prefix format single-sourced at `tax.ts:197-202` (`padStart(6,"0")`). Void leaves a permanent gap (counter advances only on commit; partial-unique index never blocks). Grep confirms zero `max()`/`nextval` in executable SQL.
- **I2 Totals computed once — HOLDS.** `tax.ts` (`roundMoney`/`computeLineAmount`/`computeSubtotal`/`computeInvoiceTotals`) is the sole implementation; SQL `save_*_draft` only casts precomputed jsonb (no arithmetic); `assertIssuable` (`validate.ts:138-192`) recomputes with the same function and blocks on `totalsMismatch`. Client forms import the same helpers. No second money-math implementation exists.
- **I3 HST + registration — HOLDS.** Single tax line on the subtotal (`tax.ts:169-176`), gate rejects a split (`validate.ts:114-116`), and the registration predicate `isRegistrationEffective` is defined once (`tax.ts:114-122`) and imported by `validate.ts` — no second copy.
- **I4 share_token — HOLDS.** 22-char base62 via rejection-sampled `randomBytes` (~131 bit), minted once in the issue path, never regenerated on re-send (`send/route.ts` reads `invoice.share_token` only; DB immutability trigger raises if it drifts). `/i/[token]` → 410 on void, 404 on unknown/no-PDF (`i/[token]/route.ts:68-82`).
- **I5 Storage — HOLDS.** One private bucket `invoice-pdfs` (`public=false`), credit notes under a `credit-notes/` sub-prefix (no 2nd bucket); `/i/[token]` streams bytes server-side (`new Response(new Blob([buffer]...))`, `route.ts:94-102`), never a signed-URL redirect; `Cache-Control: private, no-store`.
- **I6 Snapshot authority — HOLDS.** Snapshots written in the issue RPC (`issue_invoice.sql:80-95`), not `save_invoice_draft`; PDF + issued views read exclusively from `supplier_snapshot`/`customer_snapshot` (`invoice-mutate.ts:640-680`, `IssuedInvoiceView.tsx:75-76`), `customer_record_id` is a back-reference only.
- **I7 Immutability whitelist — HOLDS.** Status transitions whitelisted (`issued→paid|void|overdue`, `paid→overdue`; credit note `issued→void`), all other columns of non-draft rows frozen, child line/tax rows frozen when parent non-draft, and `invoice_payments` deliberately left mutable (`20260928121300:10-14`).
- **I8 One render path — HOLDS.** `pdf.tsx` `renderInvoicePdf` renders both document types via a `documentType` branch; grep confirms it is the only `@react-pdf/renderer` renderer; credit notes reuse it verbatim.

Hard constraints: **CASL transactional email HOLDS** (`resend/send.ts` — no unsubscribe/marketing/tracking, reply-to = acting owner, frozen language). **Guarded writes HOLD** (all three mutate layers take `{client, actorId, orgId}`, `actor_id` recorded on every RPC, never the service-role client for tenant writes). **Public-surface narrowness HOLDS** (`middleware.ts` adds only `"i"` to the public set). **i18n**: perfect en/fr key parity across all invoicing blocks; zero em-dashes in new copy (the 8 em-dashes present are all pre-existing non-invoicing blocks).

The clone was partly spec-directed ("mirror `20260928121000`", `spec-12-8:90`) and I8's single *render* path was correctly shared — but the byte-identical data/UI helpers were an unshared opportunity.
- **[A2] API-route auth/identity scaffolding copy-pasted across all 8 invoice route files — Med, fix-now + process lesson.** `requireUser()` (getCurrentUser→401) and `resolveAdminIdentity()` (resolveOrgIdentity+requireAdmin+slug-match→403) are re-defined as local helpers in every route: **16 definitions across 8 files** (verified by grep: `route.ts`, `[id]/route.ts`, `[id]/issue`, `[id]/pay`, `[id]/send`, `[id]/credit-notes`, `[cnId]/route.ts`, `[cnId]/issue`). `route-helpers.ts` shares `json`/`resolveOrgIdentity`/`handleError` but not the admin gate or the user wrapper. **This is the third recurrence of the pattern epic-3 [A2] and epic-4 [A1] each flagged and "fixed"** — the fixes extracted helpers *within* records/import, and the fresh invoicing subsystem re-cloned. Upstream lesson below.
- **[A3] God-components: `InvoiceDraftForm.tsx` (812 lines) and `CreditNoteDraftForm.tsx` (676) — Low-Med, defer (cleanup).** Each owns load-on-edit, ~14 pieces of state, live totals, an input builder, four inline async server actions (save/discard/issue), and the full render including two structurally-identical confirm dialogs. Extractable: the line-items editor, the dialog pair, the orchestration hook. `BusinessProfileForm.tsx` (724) is large-but-linear (inherent field count), only the logo upload/preview subsystem is a separable concern.

### Cross-story boundary lenses

- **[X1] A credit note has no amount ceiling and no double-credit prevention — Med-High, OPEN QUESTION + spec reconciliation.** `assertIssuableCreditNote` delegates verbatim to `assertIssuable` (`validate.ts:209-211`), which reconciles a credit note only against its **own** line items — it holds no reference to the source invoice. Verified: nothing in `credit-note-mutate.ts` or the routes compares the credit note's total to the invoice total or sums prior credit notes. A \$1,000,000 credit note against a \$100 invoice issues cleanly, and unlimited credit notes can each be issued. **`spec-12-8` is silent on this** — unlike the analogous payment-amount decision, which was explicitly reasoned and frozen ([BH5]). This is a genuine spec gap, not a triaged deviation. Bounded in practice by the owner-entered nature of the data and the epic's hard lawyer/CPA release gate, but it needs a policy call (below).
- **[X2] PDF-freeze retry can wedge permanently on a partial failure — Low, fix-now.** `uploadInvoicePdf` uses `upsert: false` (verified `storage.ts:95`). `ensureInvoicePdf` uploads the object, then writes `pdf_path` (null→value) and swallows all errors (`invoice-mutate.ts:701-712`). If the upload succeeds but the DB `pdf_path` write fails, every retry re-uploads → storage "already exists" → `writeFailed` (swallowed) → `pdf_path` stays null **permanently**; the object is orphaned and never linked, and `/send`'s repair hits the same wedge. Crosses the 12.4→12.5→12.6 boundary and leaves an issued legal document with no linked frozen PDF. Fix is idempotent re-freeze (`upsert:true`, safe because the bytes derive from frozen snapshots, or handle "already exists" and proceed to the one-time `pdf_path` write).
- **[X3] `void` status is handled everywhere but never written by any MVP path — Low, accepted deviation (record).** The immutability whitelist permits `issued→void`, `/i/[token]` returns 410 on void, and `IssuedCreditNoteView` gates on `!== "void"` — but grep confirms **no code path writes `status='void'`** (only read/display checks). By design the MVP correction mechanism is credit notes, not voiding; the void branches are reserved/defensive scaffolding for a future capability. Not a defect against any declared invariant; record so future retros don't re-flag it, and note the void-dependent branches are currently unreachable.
- **[X4] Credit-note issue doesn't re-check source creditability, and the issue route doesn't bind `[cnId]` to `[id]` — Low, defer/track.** `CREDITABLE_STATUSES` is checked at draft-create (`credit-notes/route.ts:55,157-159`) but `issueCreditNote` only reads the source `invoice_number` for the frozen reference (`credit-note-mutate.ts:257-274`), not its current status; and `[cnId]/issue/route.ts` uses only `cnId`, never verifying the credit note's `invoice_id` equals the path `[id]`. Latent today (source can't become non-creditable in MVP — `paid` is still creditable and `void` is never written [X3]; RLS+org scope protect the path), so low impact, but the path contract is unenforced.
- **[X5] Draft→Issue trusts a non-locking read — Low, defer/track (defensive note).** The issue RPC re-checks only `version + status='draft' + org` (`issue_invoice.sql:51-58,90-93`), not the line items/totals. The window is closed for saves that go through `save_invoice_draft` (it bumps `version`), and that is the only writer of child rows today — but the child-immutability trigger permits direct child writes while the parent is `draft` without bumping `version`, so a non-RPC child write could be frozen without re-validation. No code path does this; record the invariant "child writes must bump parent version."
- **[X6] Money is floating dollars, and invoice money columns are unconstrained `numeric` — Low-Med, defer/track.** Amounts are JS floats with epsilon-nudge rounding (`tax.ts:26-30`); invoice subtotal/tax/total/line columns are unconstrained `numeric` (only `invoice_payments.amount` is `numeric(15,2)`). Applied **consistently** with single-source math, so no TS↔SQL rounding divergence exists (the classic bug is absent because SQL does no money math — checked, clean). But `assertIssuable`'s strict `!==` reconciliation across the PostgREST string boundary is brittle to the unconstrained scale: any value written by a future non-canonical path would block issuance. A `numeric(15,2)` constraint on the invoice money columns (matching payments) would harden it.
