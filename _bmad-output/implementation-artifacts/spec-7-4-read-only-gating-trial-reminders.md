## Intent

**Problem:** Stories 7.1–7.3 record the cached access state (`organizations.subscription_status`: `trial`→`active`→`past_due`→`read_only`, plus `trial_expires_at`), but nothing *enforces* it: a `read_only` org (canceled subscription) can still create and edit data, and an expired trial never transitions out of `trial` at all because only Stripe events move state and a trial timeout fires no event. The epic also promises trial reminders (Day 12 + Day 14 emails, plus a persistent in-app banner from Day 12) so an owner converts before losing access — none of which exists. FR requires read-only on trial expiry / subscription lapse (data visible, no new entries) and the trial-conversion reminders.

**Approach:** Add a single server-side write gate driven by the cached state: any guarded mutation by an org that is `read_only` — or whose trial has expired — is rejected with a 403 while all reads continue to work. A daily `CRON_SECRET`-protected Vercel Cron lifecycle sweep flips expired trials to `read_only` (so the cached state stays truthful) and sends the Day-12 and Day-14 reminder emails via the existing Resend integration, each sent at most once. A persistent in-app banner on the authenticated dashboard shows the conversion prompt during the final trial days and a read-only notice once access is paused.

## Boundaries & Constraints

**Always:**
- The gate is single-sourced at the shared identity-resolution seam (`route-helpers`): write routes resolve a *writable* identity that asserts the org is writable; read routes (all GET endpoints) are never gated. `read_only`, and `trial` with `trial_expires_at <= now`, are the only non-writable states; `trial` (not expired), `active`, and `past_due` are writable (a failed-payment customer in `past_due` is still mid-dunning and must not be locked out — NFR-R4).
- **Decision — block all guarded mutations.** In a non-writable state every write that flows through the guarded layer is rejected: create, edit, and delete of records; team invites; spreadsheet import; and all invoice actions (draft, issue, record-payment, send, credit-note). There is no per-operation exemption for edits-to-existing or invoice bookkeeping — reads remain the only allowed access.
- `subscription_status` + `trial_expires_at` are read as part of the org-by-slug lookup that identity resolution already performs (no extra query), and the writable check is a pure predicate over those two fields plus the current time.
- A blocked write returns `AppError(403, "readOnly")` surfaced through the standard `{ data, error }` envelope / `handleError`; raw internals are never leaked. The predicate treats an expired trial identically to `read_only` so gating is correct even if the cron has not yet flipped the row.
- The cron route is protected by `Authorization: Bearer ${CRON_SECRET}` (missing/invalid → 401, no work); it reads/writes via the service-role admin client (no user session). The flip (`trial` + expired → `read_only`) and each reminder send are idempotent: reminders are stamped with per-stage sent timestamps so repeated runs never re-send.
- Trial reminders target the trial state only (Day 12 ≈ 2 days before expiry, Day 14 ≈ at expiry); emails reuse the Resend client + error pattern in `src/lib/resend/send.ts`, localized EN/FR from the i18n catalogs, no em-dashes. The in-app banner reads `trial_expires_at` + `subscription_status` passed from the server layout and is WCAG AA, reduced-motion aware, with `role="status"`/`role="alert"` as appropriate.
- Billing CTAs stay Admin-only (Member RBAC excludes billing): the banner's "Add billing" action renders only for admins; members see the notice without the billing CTA.

**Never:**
- Never gate reads, seeding, the Stripe webhook's own status writes, or claim-time demo-data clears (those run pre-claim with a null/active trial clock and are naturally writable; the gate must not block them).
- Never add new `subscription_status` states — `read_only` already exists (7.3); `grace`/`deleted` and the 30-day offboarding/cascade-delete belong to Epic 8. Never collect payment, build billing UI beyond the banner CTA (Checkout/Portal are 7.2/7.3), or build the tier-change prompt / reconciliation cron (7.5).
- Never introduce usage meters, quotas, or spend caps (flat-tier model). Never send dunning/failed-payment emails here (Stripe owns those); reminders are trial-only. Never silently infer a subscription lapse from Stripe/webhook downtime — only an explicit expired trial or a recorded `read_only` blocks writes.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Write while writable | Org `trial` (not expired) / `active` / `past_due`; any guarded mutation | Mutation proceeds unchanged | Existing error paths unchanged |
| Write while read-only | Org `subscription_status='read_only'`; create/edit/delete/invite/import | Rejected before the mutation | `AppError(403,"readOnly")` |
| Write while trial expired | Org `trial`, `trial_expires_at <= now` (cron not yet run) | Rejected (expired trial == read-only on the fly) | `AppError(403,"readOnly")` |
| Read while read-only | Org `read_only`; any GET (records, invoices, schema) | Data returns normally (visible, no gate) | N/A |
| Cron: trial expired | Daily sweep, org `trial` + `trial_expires_at <= now`, valid `CRON_SECRET` | Org flipped to `read_only`; Day-14 email sent if not already; idempotent | Resend failure logged; flip still applied |
| Cron: 2 days left | Org `trial`, `now >= trial_expires_at - 2d`, not expired, Day-12 not sent | Day-12 reminder email sent; `trial_reminder_day12_sent_at` stamped | Resend failure logged; no stamp so it retries next run |
| Cron: already sent | Reminder stage's `*_sent_at` already set | No re-send (idempotent) | N/A |
| Cron: unauthorized | Missing/invalid `Authorization: Bearer CRON_SECRET` | Rejected, no reads/writes | 401 |
| Banner: converting | Dashboard, org `trial`, `0 <= daysRemaining <= 2` | Persistent conversion banner "Your trial expires in N days…"; admin sees Add-billing CTA | N/A |
| Banner: read-only | Dashboard, org `read_only` or expired trial | Read-only notice; admin sees Add-billing CTA, member sees notice only | N/A |
| Banner: hidden | Org `trial` with `daysRemaining > 2`, or `active` | No banner | N/A |

## Implementation Notes

- **The gate.** `src/lib/billing/access.ts` holds the pure `isReadOnly(status, trialExpiresAt, now)` predicate + `assertWritable({subscription_status, trial_expires_at})` (throws `AppError(403,"readOnly")`). `route-helpers` extends `OrgIdentity` + `resolveOrgIdentity`'s select with `subscription_status, trial_expires_at` (free, same lookup) and adds `resolveWritableOrgIdentity` / `resolveWritableAdminIdentity` wrappers that assert *after* the admin/member gate — so a non-admin still gets `forbidden`, not `readOnly`. Every guarded write route switched to the writable variant (records POST + `[id]` PATCH/DELETE; schema fields/columns; business-profile logo via writable resolver, PUT via explicit `assertWritable` since it keeps its local admin resolver; import/commit via `assertWritable` after `resolveImportRequest`, which now carries the access fields; invite via `requireAdmin` + org read + `assertWritable`; all invoice writes). GET siblings stay on the plain resolver (reads never gated). The pure `mutate()` primitive is untouched, so seeding/claim-clears are never blocked.

- **BH-9 / EC-4 / EC-claim-1 / EC-claim-2 (blind + edge-case) — reject.** (a) Banner `Math.ceil` day math vs the matrix's `0 <= daysRemaining` lower bound: the code treats day-0 as expired/read-only (more correct); the only fix would edit this build's spec matrix → reject by rule. - **EC-5 (edge-case) — `low` → reject.** "Invite route defaults a null org read to writable `trial`/null." `membership.orgId` comes from a successful `requireAdmin`, so the org row exists; a null read requires a delete race, and the `trial`+null default is a benign writable state that `inviteMember`'s own org operations would then fail on anyway → reject.

## Design Notes

- **Single chokepoint, resolver-level.** Every write route already resolves `{ client, actorId, orgId }` through `resolveOrgIdentity`/`resolveAdminIdentity`, and that lookup already reads the org row — so adding `subscription_status`/`trial_expires_at` to the select is free and the gate costs no extra query. Gating is kept out of the pure `mutate()` primitive because it is identity-agnostic and reused for seeding/claim-clears, which must never be blocked; the writable-resolver variants make write-vs-read gating explicit and greppable while leaving reads open.
- **Expired trial == read-only, computed on the fly.** The `isReadOnly` predicate treats an expired `trial` as non-writable immediately, so enforcement is correct even between the expiry instant and the next cron run (cron lag never grants a free write). The cron additionally *persists* the `trial`→`read_only` flip so the cached state and the banner reflect reality. `past_due` stays writable: a failed-payment customer is mid-dunning (Stripe retries), and NFR-R4 forbids locking out a paying user on a transient state.
- **Idempotent reminders.** Per-stage `*_sent_at` timestamps (not a counter) make each reminder exactly-once across repeated daily runs; the stamp is written only after Resend succeeds, so a transient send failure retries next run rather than being silently skipped. The Day-14 email and the read-only flip happen in the same sweep pass for an expired org, keeping their timing consistent.
- **One cohesive cron.** A single daily `/api/cron/trial-lifecycle` route owns both the trial-expiry flip and the two reminder stages (the epic notes one Vercel Cron mechanism runs the trial/offboarding sweeps); 7.5's reconciliation cron and Epic 8's offboarding sweep are separate and out of scope here.
- **Banner data flow.** No org context provider exists; the server layout fetches the two fields and passes `daysRemaining` + `subscriptionStatus` + `role` as props to the client `TrialBanner`, matching the settings-page server→client prop pattern.
