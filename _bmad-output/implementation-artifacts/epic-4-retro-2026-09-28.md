- **[A2] Committed cell values are written as raw strings with no type coercion — Med, defer (partly tracked).** `commit.ts:159-166` builds each payload as `payload[fieldKey] = row[sourceColumn] ?? ### Spec-to-implementation reconciliation

Mandatory Technical Decisions from `epic-4-context.md` **confirmed in code:** server-side-only parse (`analyze/propose/commit` all `Buffer.from(await file.arrayBuffer())` → `parseSpreadsheet`, never client rows); two-phase invariant (analyze/propose import no mutation layer — only `commit/route.ts` imports `bulkInsertRecords`); guarded writes through `mutate.ts` under the RLS-scoped client with explicit identity and **no service-role for tenant rows** (service role only inside `requireAdmin`); Schema-Validator gate (targets resolved against non-hidden `getSchema` fields via `normalizeTableName` in both `sanitizeProposal` and `planCommit:123-130`); idempotency (`import-${importId}-${tableKey}-${rowIndex}`, `commit/route.ts:169`); synthetic clear scoped to `SYSTEM_ACTOR_ID` + `deleted_at IS NULL` + affected tables (`commit/route.ts:193-202`); relation targets dropped, not written (`commit.ts:134-136`); `{data,error}` envelope with translation-key errors; en+fr copy, no em-dash in new keys.

- **[S1] Write strategy — "delete then insert, one transaction" vs the as-built "insert then clear, no transaction" — Low, reconcile spec.** `epic-4-context.md:35` says "Soft-delete synthetic ... **then** bulk-insert ... in **one transaction**." As built the order is **inverted for crash-safety** (insert first, then clear — `commit/route.ts:156-210`) and there is **no DB transaction** (the Supabase JS client can't span statements without an RPC, and the epic bans DDL/RPC sprawl; atomicity comes from single-statement array inserts + idempotency + ordering — `spec-4-4` Design Notes). This is a sound, documented deviation; reconcile the epic-context wording so a future reader isn't misled into expecting delete-first / a transaction.

### Diff-scope review (cross-story boundary lenses)

- **[D1] Duplicate-target columns silently collapse at commit (last column wins) — Low/Med, fix-now-or-track.** Nothing across the pipeline resolves two source columns pointed at the **same** `{table, field}`: 4.2 explicitly "preserves duplicate targets ... left for 4.3" (`spec-4-2` Design Notes); 4.3's picker lets any column pick any field and its readiness gate checks only `unresolved` (`resolve.ts:69-85` — no duplicate detection); and `planCommit` writes `payload[fieldKey] = row[sourceColumn]` once per resolved target (`commit.ts:161-164`), so for two columns → one field the **last-listed column overwrites the first**, silently dropping data with no warning to the Admin. Each story deferred the concern to the next and the commit-time consequence was never examined. Detect duplicate resolved targets in the readiness gate (warn or block), or surface it at commit.
- **[D2] Multi-table commit has a partial-write window if the user abandons a failed retry — Low/Med, accept/track.** `commit/route.ts:163-184` inserts table-by-table in a loop, and the synthetic clear runs only **after all** inserts (`:189`). If table 2 throws after table 1 committed, table 1's real rows persist, synthetic rows stay uncleared, and the client shows `commitFailed`. An idempotent retry converges (table 1 dedupes via the pre-check, table 2 inserts, clear re-runs), so the **recovery path is correct** — but a user who does not retry is left with a partial multi-table import. This is a whole-pipeline property no single story owned. Accept for MVP (retry is the documented recovery); track.
- **[D3] `bulkInsertRecords` real-DB write path is unit-untested — Med (verification), track. The 42P10 near-miss is the epic's clearest lesson.** `mutate.ts:140-202` is the **sole tenant write** in the import pipeline, yet route tests mock the mutate layer and `mutate.test.ts` exercises the pre-check / 23505 branches only against a fake client — no test runs the real array `.insert` against Postgres. The first implementation used `.upsert({ onConflict: "...idempotency_key", ignoreDuplicates: true })`, which would have **failed every commit** (`42P10` — a *partial* unique index cannot be inferred as an `ON CONFLICT` arbiter). It was caught **only** by a manual `EXPLAIN` against the live DB (`spec-4-4` Implementation Notes), not by the green mocked tests. The mocked-test blind spot on the write path is real and recurring (`deferred-work.md` already logs the 1.2 idempotency-race branch as untested for the same reason). Add a real-Supabase integration test for `bulkInsertRecords` (fresh-batch insert, idempotent re-run, 23505 path).
