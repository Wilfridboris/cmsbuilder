# Epic 13 Retrospective — List-of-Values (Single-Select) Field Type

## Epic summary

**Epic 13** added a single-choice picklist field type (`select`) threaded through every data-entry surface: the data model & validator, the guarded schema-mutation layer, the Conversational Editor (chat), the dropdown UI (table/card display, add form, inline edit), AI generation + hard-fallback, public intake forms, and CSV import. The type is deliberately minimal for MVP (plain styling, single-select only) with a **governing append-only invariant**: add a value, rename a value's display label (stored `value` key stays stable), archive an in-use value — never delete an in-use value, never mutate a stored key, no row migration.

## Findings

Each finding carries a source reference. Severity is this retro's consolidated call after re-checking the two review agents' reports against primary source. Disposition: **fix** / **defer** / **accept**.

### Spec-to-implementation reconciliation

- **F1 — Admin-only inline "+ Add value" dropdown affordance not built (Med, defer — already tracked).** The epic context (lines 20, 53) and story 13.2 describe an Admin-only "+ Add value" affordance inside the dropdown. `SelectDropdown.tsx:62,118-123` reserves `addValueSlot`, but **no caller passes it** (`grep addValueSlot src/` → declarations only). This was a *conscious* deferral, not a silent drop: `SelectDropdown.tsx:39` says "The add-value affordance is deferred to Story 13.4," and `deferred-work.md` records it twice with a full follow-up scope (new Admin-gated `POST /api/schema/select-options`, `AddSelectValueControl.tsx`, role/slug threading, i18n, tests). It does **not** break the declared success criterion ("values … managed entirely from chat" — which works). Disposition: accept-as-deferred; keep tracked.

- **F2 — `RecordDetail` has no select editor; editing a select degrades to a free-text input (Med, fix/defer).** `RecordDetail.tsx` renders a select's label for display (via `formatCell`) but its `FieldEditor` (`RecordDetail.tsx:241-357`) has no `select` branch, so editing falls through to the generic text `Input`. This surface is the **anonymous `/generate` demo reveal** (only `DemoDashboard.tsx:396` imports it; `Dashboard` namespace; "changes stay in this preview only"), so edits are non-persisted and the blast radius is a pre-account preview UX inconsistency. Still a divergence from "dropdowns render on every data-entry surface." Disposition: fix (add a select branch) — low effort, or defer with tracking.

- **F9 — Behavior beyond spec: `matchSelectValue` accepts case-insensitive label on intake as well as value token (Low, accept).** `select-input.ts:111-114` matches by value then by case-insensitive label. Intended for CSV import (external label text); the intake client only ever submits tokens, but it shares the matcher so a label string would also be accepted on intake. Benign — it always resolves to a legitimate non-archived option's canonical value. Disposition: accept.

### Code lenses (adversarial / edge-case / verification-gap)

- **F3 — `rename_select_option` has no label-collision guard → ambiguous label-based CSV import (Med, fix).** `validateRenameSelectOption` (`validator.ts:1012-1015`) checks only that the new label is non-empty; it never checks the label against other options. `validateAddSelectOption` enforces **value** uniqueness (`validator.ts:965-967`) but nothing enforces **label** uniqueness. Because `matchSelectValue` resolves import/intake cells by case-insensitive label with first-match-wins (`select-input.ts:112`), an admin who renames option B's label to equal option A's label makes a label-based CSV import cell route to whichever option appears first. The append-only invariant on `value` is intact (no corruption of existing rows); the exposure is mis-routing a *new* import cell. Narrow (requires the rename + a label-keyed import), but it is a genuine data-integrity path. Disposition: fix — reject a rename/add whose label collides (case-insensitively) with another active option.

- **F6 — `handleAddSelectOption` doc comment overstates its enforcement (Med→Low, fix).** `edit/route.ts:867-869` claims the target "is enforced against the select field shown in the summary." It is not — the handler passes straight to the mutator and relies on `validateAddSelectOption` → `findSelectField` for target safety (which is correct and safe). The behavior is sound; the comment is a latent trap for the next editor. Disposition: fix (correct the comment).

- **F4 — `findSelectField` matches the field key un-normalized (Low, fix/accept).** `findSelectField` normalizes the *table* key (`validator.ts:906`) but matches the *field* key raw (`validator.ts:911`), unlike the add-field path which normalizes. A model returning a non-normalized `fieldKey` (e.g. `"Status"`) makes all three value ops reject (no corruption — fail-closed). Disposition: fix (normalize the field key for consistency) or accept.

- **F5 — `matchSelectValue` label match folds case but not accents (Low, defer).** Stored `value` tokens are accent-folded by `normalizeTableName`, but label matching only lowercases (`select-input.ts:112`). On French data a CSV cell whose accents differ from the stored label is treated as invalid and rejects the whole commit. French/Ontario is a target locale. Disposition: defer (consider accent-folding the label compare).

### Aggregate / structural

- **F7 — Low-grade duplication across the new surfaces (Low, accept/cleanup).** Archived-filter rule appears in the shared helper (`select-input.ts:35,106`) and is **re-implemented inline** in `IntakeForm.tsx:291` — deliberate per the 13.6 spec (the public form must not import dashboard-coupled components), so accepted. "Blank → omit" logic repeats in three small pure spots (`selectDraftToData`, `matchSelectValue`, `coerceImportValue`); `findSelectField` (validator) and `buildTargetIndex` (import) are two independent "find non-hidden field + read options" walkers. All low-value cleanup. Disposition: accept.

- **F8 — God-file watch: `validator.ts` 1499 lines, `api/schema/edit/route.ts` 1094 lines (Low-Med, defer).** Growth is cohesive — a flat set of single-purpose validator functions sharing small primitives, and a `kind`-dispatched route with one focused `handle*` per op. No shared mutable state. But the three select-option route handlers are near-identical boilerplate copies, and both files are now large enough that a split (`validator/select-ops.ts`; a table-driven handler helper) would aid readability. Disposition: defer (watch item).

### Adjacent (not epic-13-introduced, surfaced during review)

- **A1 — No server-side select-option membership guard on the authed write path (Low, defer — tracked).** The untrusted surfaces (public intake, CSV import) are fully server-validated via `matchSelectValue`, and fail closed. But `src/lib/data/mutate.ts` (the authed add-record / inline-edit write path) is **not** in the epic-13 diff and has no select-option membership check (unlike the relation referential-integrity guard). A direct authed API write could persist an off-list token. Acknowledged in `deferred-work.md` as net-new hardening. Disposition: defer.

- **A2 — Em-dashes in pre-existing user-facing `fallback.ts` `reason` strings (Low, cleanup).** Epic-13's own user-facing copy is clean (verified: no em-dash in the new i18n keys or the two new select fallback reasons). But pre-existing `generation/fallback.ts` `reason` strings (`:42,55,88,114,134,166`) use em-dashes and are user-facing, violating the no-em-dash rule; and `gemini/prompts.ts:301` both contains an em-dash and instructs the model not to use one. Not introduced by this epic. Disposition: cleanup (optional).

### Confirmed strengths

- **Append-only invariant holds structurally.** Archive is a flag-flip that never removes the option object (`overrides.ts:356`; refuses the last active / already-archived option at `validator.ts:1062-1073`); rename edits `label` only, `value` never written (`overrides.ts:338`); add enforces value uniqueness against **active and archived** options (`validator.ts:962-967`) so a retired token can't be shadowed. Verified directly in `schema-mutate.ts`, `overrides.ts`, `validator.ts`.
- **RBAC enforced.** Every option op dispatches only after `resolveWritableAdminIdentity` (`edit/route.ts:222`) and the `assertEditorOperationAllowed` fence (`:310`). The new route **adopted the shared writable-admin resolver** (comment cites "retro [A1]") — good adherence to the epic-7 route-auth process lesson.
- **Untrusted surfaces fail closed.** One shared `matchSelectValue` authority for intake + import; CSV import rejects the whole commit (zero partial write) and names the field + distinct bad values on any unmatched cell (`commit.ts:311-319`); intake rejects forged/archived tokens with a generic 400 (no public field leak).
- **Blocklist intact/unchanged** (`validator.ts:138-144`); the new op names contain no blocked verb.
- **Generation hardened:** the prompt teaches `select` with owner-named options only (no hallucinated choices; `needs_clarification` otherwise) and even instructs the model "Do not use an em-dash."
- **Strong test coverage** (1436 tests; large epic-13 additions across validator/route/mutate/matcher), type-check clean.
