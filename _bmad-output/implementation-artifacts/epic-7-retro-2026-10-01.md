### Cross-story boundary findings (the state-machine seams)

The `subscription_status` state machine spans all 5 stories; these are the seams no single session saw both sides of. Each verified against primary source.

- **[F7] Trial-cron expiry flip is not status-guarded, so it can clobber a concurrent checkout→active and lock out a paying org — MED, fix-now.** `trial-lifecycle/route.ts:145-151` flips the expired-trial row with `.update({subscription_status:"read_only"}).eq("id", org.id)` — filtered on `id` ONLY. The scan is scoped to `trial` (`:126`), but between the scan and the per-row UPDATE a `checkout.session.completed` can set the row `active` (`webhook/route.ts:179`); the cron then overwrites that fresh `active` back to `read_only`. An org that pays in the final minutes of its trial, concurrent with the daily sweep, is wrongly locked out — and recovery then needs a *fresh* checkout (an `invoice.paid` would be skipped by the read_only-terminal guard). This contradicts the spirit of NFR-R4 (never lock out a paying user). Contrast `claim.ts:271`, which deliberately adds a `.is(...)` guard for exactly this idempotency reason. Fix: add `.eq("subscription_status","trial")` to the flip UPDATE (a one-line, mirror-of-claim guard). **No test covers the clobber direction** (the reverse, checkout reactivating a read_only org, IS tested — `route-stripe-webhook.test.ts:411-432`).
- **[F1] `past_due` is writable-forever if Stripe is not configured to cancel after failed dunning — MED, open question + release prereq.** The gate deliberately keeps `past_due` writable (NFR-R4, mid-dunning). The only exits from `past_due` are `invoice.paid`→active or `customer.subscription.deleted`→read_only (`webhook/route.ts:206-270`); no handler or cron escalates a long-lived `past_due`. If Stripe's dunning is configured to leave the subscription uncollectible-but-active (a Dashboard option) rather than cancel, `subscription.deleted` never fires and the org stays fully writable without ever paying. No story owns the "past_due has lasted too long" escalation. Mitigated by correct Stripe Dashboard config (smart-retries → cancel at end of schedule), which the specs already note is a Dashboard/release concern. **No test asserts any `past_due` bound.**
- **[F2/F11] Out-of-order first-invoice can mis-transition or silently no-op a brand-new subscription — LOW-MED, defer/track.** `handleInvoiceStatus` guards only `read_only` (`webhook/route.ts:260`), so a resolvable `trial` org receiving an out-of-order `invoice.payment_failed` before its `checkout.session.completed` is processed would be written straight to `past_due` (losing the trial banner); and the first `invoice.paid` of a new subscription can arrive before `checkout.session.completed` persists `stripe_subscription_id`, so org resolution falls back to invoice `parent.subscription_details.metadata` — which Stripe only echoes if the `.dahlia` invoice payload carries it. A pure trial org (no checkout yet) is NOT resolvable (null `stripe_subscription_id`, no stamped metadata), so the harmful path requires the subscription to exist (metadata stamped) while the org row is still `trial` — a narrow Stripe-ordering window. End state usually self-corrects because `checkout.session.completed` writes `active` unconditionally. Real but bounded; the ordering assumption is **asserted by no test** (the resolution *shapes* are tested, `route-stripe-webhook.test.ts:309-347`, but pre-seed the metadata the live assumption depends on).
- **[F9] Upgrade-prompt cycle window uses the current cycle's length to reach back for the prior cycle — LOW-MED, defer/track.** `resolveTierView` computes `lastCycleStartSec = periodStart - (periodEnd - periodStart)` (`settings/page.tsx:92-94`). Monthly Stripe cycles are 28–31 days, so using the current month's length to anchor the previous month's window can start the "last completed cycle" a day off, over/under-counting issued invoices for an org sitting exactly at a band boundary and wrongly firing/suppressing the FR55 prompt. (The UTC-date-truncation sub-concern was already triaged in 7.5 BH-1 as internally consistent — `issue_date` is stamped with the same UTC slice — so only the uneven-cycle-length approximation is novel.) Advisory prompt + provisional bands bound the impact. **The period-math seam has no test** — `tier-prompt.test.ts` only drives the pure predicate with hand-fed counts; `resolveTierView` and `countIssuedInvoicesInPeriod` boundary behavior are a verification gap.
- **Seams checked and CLEAN:** tier mapping is identical across checkout webhook, reconcile cron, and the tier view (all funnel one Stripe price id through `priceIdToTier` — so reconcile does NOT false-alarm drift; `tiers.ts:98-108`, tested `route-cron-reconcile-tier.test.ts:104-121`); `read_only` is terminal across both invoice handlers AND the cron, exit only via checkout (`webhook/route.ts:260-267,206-221`; tested `:285-432`); the gate handles every `SubscriptionStatus` value the webhook/crons can write (`db.ts:104` enumerates exactly the four `access.ts` handles); the trial-cron flip is decoupled from the email send, so a Resend failure never blocks the flip (`trial-lifecycle/route.ts:143-163`).

### Aggregate / architecture findings

- **[A1] The read-only gate is not the single chokepoint the code claims — MED, fix-now-small + process lesson.** `route-helpers.ts` documents the writable resolvers as "the single write-vs-read seam: every guarded write route resolves THIS variant" (`:92-94`), but **four routes bypass the resolver and call `assertWritable` inline on their own re-read of the org row**: `invite/route.ts:91`, `business-profile/route.ts:134` (PUT), `business-profile/logo/route.ts:70`, `import/commit/route.ts:63`. Functionally gated today (so no security hole — confirmed every mutation route is either writable-resolved or inline-asserted, and every GET is ungated), but the documented invariant is false and the assertion lives in two idioms. A future change to the gate (new non-writable state, or a change to the `AccessFields` read) will silently miss these four because they feed `assertWritable` from their own queries, not from `OrgIdentity`. `invite` and `logo` additionally re-default a missing status to `"trial"` inline (`invite/route.ts:92`).
- **[A2] `business-profile/route.ts` ships a private copy of the shared `resolveAdminIdentity` — MED, fix-now + process lesson (RECURRENCE).** `business-profile/route.ts:61-68` defines a local `resolveAdminIdentity` byte-identical to the shared `route-helpers.ts:128-138` export, instead of importing it (and then bolts `assertWritable` on by hand). **This is the fourth recurrence of the route-auth-duplication pattern that epic-3 [A2], epic-4 [A1], and epic-12 [A2] each flagged and "fixed"** — the prior fixes extracted helpers *within* the records/import/invoice subsystems, and each fresh route surface re-clones. The upstream lesson (below) is now a standing pattern, not a one-off.
- **[A3] Three new duplication clusters, each self-admittedly "mirroring" a sibling — MED (2a/2c) / LOW (2b/2e), defer (cleanup).** (a) `trial-reminder.ts` is a near-verbatim clone of `send.ts`: `escapeHtml` character-identical (`trial-reminder.ts:55-61` vs `send.ts:49-55`), the full HTML email scaffold duplicated (`:100-127` vs `:76-103`), and the lazy-env + `AppError(502,"sendFailed")` + Resend send/catch tail structurally identical (~60 lines); a shared `renderTransactionalEmail` + `sendTransactional` would collapse it. (b) `BillingStart` / `BillingManage` / `TierView` triplicate the same `fetch`+`useState`+`window.location.href` redirect machine, the `ERROR_KEYS` set, the `resolveError` closure, and the reduced-motion `reveal` object verbatim (`BillingStart.tsx:31-86` ≡ `BillingManage.tsx:32-84` ≡ `TierView.tsx:37-122`); BillingManage and TierView even POST the same `/api/stripe/portal` — a `usePortalRedirect(slug)` hook + shared error-alert would remove it. (c) Lower-value: the two cron routes duplicate the auth/scan/summary scaffold (`trial-lifecycle:109-113` vs `reconcile-tier:69-73`); `reportError`/`reportCritical`/`reportRejection` repeat the DSN-gate+lazy-load skeleton three times (`report.ts:46-101`).
- **[A4] `settings/page.tsx` has accreted billing orchestration into a page component — MED, defer (cleanup).** Now 283 lines (+203 across the epic, touched by 4 stories). `resolveTierView` (81 lines, `:57-138`) is domain logic — a live Stripe `subscriptions.retrieve`, billing-period arithmetic, and an RLS invoice-count orchestration — living inline in a view module and pulling the Stripe SDK + a Supabase RLS client into the page. Belongs in `lib/billing/`. (The webhook at 411 lines was checked and is **not** a god-file: single responsibility, a clean switch dispatching five focused handlers + small helpers; the length is defensive Stripe-shape handling. Not flagged.)
- **[A5] Minor pattern divergences — LOW, accept/record.** The webhook returns bare `{error}` / `{received:true}` rather than the `{data,error}` envelope (`webhook/route.ts:51-80`) — defensible (Stripe is the client, and the raw-body/signature path must precede any helper), recorded so a reader does not assume `ApiResponse`. Redirect-state copy is keyed three ways with identical English (`Billing.redirecting`/`manageRedirecting`/`upgradePromptRedirecting`), mirroring the triplicated components. The two email modules use different interpolation engines (`send.ts` manual `.replace`, `trial-reminder.ts` `IntlMessageFormat`) — not a bug today, but a pluralized invoice string would silently fail to format. `server-only` discipline and writable-assert-after-admin-gate ordering were both checked and are **uniform/clean**.
