### Aggregate views

- **[A1] The public intake write reads `org_schemas` twice per POST — Low/Med, defer (fold into open epic-3 item 21).** Each submission to the one unauthenticated endpoint does: (1) `getIntakeTarget(slug)` → `getSchema(admin, org.id)` (`route.ts:69` → `intake.ts:84`), then (2) `mutate(..., "insert", ...)` → `insertRecord` → `assertRelationReferencesExist` → `getSchema(client, orgId)` (`mutate.ts:227,373`). So one POST is 1 org lookup + **2** schema reads, even though `getIntakeTarget` already resolved the schema-derived target and fields. The intake payload never contains relation keys (the allowlist drops them), so the second read's relation-integrity check does no useful work on this path — it is a pure wasted round-trip. This is exactly the still-open **epic-3 item 21** ("pass the resolved schema into `mutate` to drop the per-write `getSchema` round-trip") — epic 6 is a fresh instance where the schema is already in hand at the call site. *Note:* the `deferred-work.md` abuse-protection entry (line 172) undercounts this as "two DB reads (org lookup + getSchema)"; it is three. Not a defect (the writes are correct); efficiency/track, best landed with item 21's `mutate` schema-passthrough rather than as a bespoke intake fix.
- **[A2] Architecture is clean and `server-only` was applied proactively — win (not a finding).** All four new server modules carry `import "server-only";` as line 1 (`intake.ts:1`, `api/intake/[slug]/route.ts:1`, `org-recipients.ts:1`, `intake-notification.ts:1`) — the epic-5 [A2] lesson (a data module missing the `server-only` guard) applied here without a retro prompting it. No `"use client"` component imports a server data module at runtime: `IntakeForm` is `"use client"` and reaches the server strictly through `fetch` (`IntakeForm.tsx:148`). Every write goes through the guarded `mutate.ts` — no reach-around service-role write. The new public surface (`/forms/[slug]` page + `/api/intake/[slug]`) mirrors the established `/i/[token]` shape (`force-dynamic`, `runtime="nodejs"`, admin client, data-free failure to a friendly state) and is correctly registered as public (`middleware.ts` `PUBLIC_TOP_LEVEL += "forms"`, with a new middleware test closing the 6.1 VG1 gap).
- **[A3] Recipient resolution was de-duplicated the right way — win.** `resolveAdminEmails` / `resolveOrgLanguage` were extracted *verbatim* from the trial-lifecycle cron into a shared `src/lib/orgs/org-recipients.ts` (itself `server-only`), and the cron now imports them (`trial-lifecycle/route.ts:9-12,224,230`). This is the inverse of the route-auth duplication theme that recurred across five prior epics: a second consumer prompted **extraction**, not another copy. Cron behavior is unchanged (AC5 of 6.4; the trial-reminder/cron suites are green in the 1332).
- **[A4] The epic-5 route-auth convention gate held on the first new route after it landed — win/note.** `/api/intake/[slug]` is a public no-auth write that *deliberately* does not route through `resolveWritableAdminIdentity` (6.2 BH1, a human decision: lead capture must never be billing-gated, or an anonymous visitor would be 403'd and the owner's billing state would leak to strangers). It uses neither `requireAdmin(` nor `resolveWritableOrgIdentity(`, so `tests/unit/route-auth-convention.test.ts` (epic-5 item 72) correctly does **not** flag it. The gate's "either primitive alone is fine" scoping proved right on its first real exercise against a new route.

- **[S1] A boolean field makes the "at least one field filled" guard vacuous — Low, accept (documented).** Both the client (`IntakeForm.tsx:138-139`) and the server (`route.ts:112-116`) note that a boolean always writes a value, so a form containing *any* boolean field can never be "empty": an all-blank submission still writes `{boolean: false}`, passes the non-empty check, persists a near-empty lead, and triggers the owner email. This is documented intended behavior and low-impact (intake tables are rarely boolean-bearing; neither rich fixture had a boolean field, so it is unit-covered only), and the broader "unbounded public write" surface is already the deferred Epic-14 anti-abuse story. *Reconciliation:* record as an accepted deviation so later retros stop re-flagging it; revisit when the Epic-14 anti-abuse story lands.

### Diff-scope review (cross-story boundary lenses, narrowed)

**Seams checked and found clean:**
- **Relation exclusion is triple-enforced and pinned end-to-end.** Render path drops `relation` fields (`intakeFields` `target.ts:69-73`); the POST allowlist iterates only `target.fields` and silently drops any other submitted key, including an injected relation key (`route.ts:74-109`); and Story 6.5's `tests/unit/intake-relation-exclusion.test.ts` pins the whole FR78 invariant in one file against a relation-bearing fixture (a `one` relation, a `many` relation, and a hidden scalar) — the render derivation yields only visible scalars, and injected `client`/`crew` keys never reach the written record. A regression on any one of the three layers fails a test. No target-record labels/counts can leak because the public path never fetches related records.
- **The realtime filter stays org-scoped only** (`recordsChangeFilter`, guarded in `realtime.test.ts`, 6.3): the invariant that lets anonymous `INTAKE_ACTOR_ID` rows reach the owner's subscription exactly like a dashboard write, with no actor predicate. The hook is payload-agnostic (invalidates on any event, never inspects `actor_id`), so no intake-specific wiring was added.
- **Email is strictly downstream of a confirmed write** (`route.ts:122-160`): the notification block runs only after `result.error`/`!result.data` is cleared, inside one try/catch that reports and swallows, so the submitter always gets `200` (FR28). The summary iterates only `target.fields`, so no relation data reaches the email (FR78).
- **`INTAKE_ACTOR_ID` is distinct from `SYSTEM_ACTOR_ID`** (`mutate.ts:39,51`) so intake leads are attributable and never confused with synthetic/demo rows; real leads are not swept by the claim-time synthetic-data clear (lifecycle timing, documented at `mutate.ts:44-50`).

No cross-story finding surfaced beyond [A1]. The relation-exclusion fence — the epic's highest-risk privacy property (no client-list leak to anonymous submitters) — is the most thoroughly guarded seam in the epic.
